# App Factory

How an app idea becomes a repository an AI agent can start building in.

## The flow

1. **Idea** — Ray asks for app ideas in conversation. Each idea is filed here
   as an issue using the **App Idea** form
   (`.github/ISSUE_TEMPLATE/app-idea.yml`), which carries the name, the
   one-line description, the rationale, the visibility and an optional target
   owner. Ideas are *not* generated by a workflow; this step is deliberately
   human. New repos land in the `RokctAI` org by default (see
   [Configuration](#configuration)).
2. **Acceptance** — Ray reads the issues and applies the `approved` label to
   the one he wants built.
3. **Spawn** — `app_spawn.yml` fires on that label, parses the form, checks
   the target repo does not already exist, and calls `app_create.yml`.
4. **Seed** — `app_create.yml` creates the repo, seeds it from
   `templates/app/`, pushes `main`, and opens a **Build v0** issue in the new
   repo pointing at `docs/spec.md`.
5. **Close** — the originating issue gets a comment with the new repo URL and
   is closed.

If parsing fails, the slug is invalid or the repo already exists, the
workflow comments the reason on the issue and removes `approved`, so
re-applying the label retries.

## Labels

| Label | Applied by | Meaning |
| :--- | :--- | :--- |
| `app-idea` | the issue form, automatically | This issue is a candidate app. |
| `approved` | Ray, by hand | Build it. Triggers the spawn. |

Both labels must be present for the spawn to run; `approved` on anything
without `app-idea` is ignored.

## Configuration

- **`vars.FACTORY_TARGET_OWNER`** — repo variable naming the GitHub user or
  org new repos are created under. Defaults to **`RokctAI`** when unset. The
  issue form's *Target owner* field overrides it per-idea, and setting the
  variable overrides the default for every idea.

  **The casing is load-bearing.** `initiate.py` decides whether a repo is an
  org repo by testing the literal substring `RokctAI/` against the git origin
  URL — case-sensitively, in three places (`:356` for the `.rok` skill,
  `:370` for the Protocol workflows, `:484` for the workspace route). GitHub
  itself is case-insensitive about owners, so `gh repo create rokctai/foo`
  lands in the same org — but the remote the spawn writes is the string it was
  given, and a lowercase `rokctai/foo` origin fails all three tests. Spell it
  `RokctAI`, in the variable and in any per-issue override.

- **`secrets.MONOREPO_PAT`** — the existing cross-repo token, used by default.
  With `RokctAI` as the target owner this is the expected credential: it is
  already the org-facing token the rest of the factory uses, so provided its
  scopes cover repo creation (see below) nothing new needs issuing.
- **`secrets.FACTORY_PAT`** — optional override. When set, the spawn uses it
  instead of `MONOREPO_PAT`. Actions cannot look a secret up by a name held
  in a variable, so the override is a second secret rather than a
  `FACTORY_PAT_SECRET_NAME`-style indirection. It exists for the case where
  `MONOREPO_PAT` can push but not create — nothing about the `RokctAI` default
  requires it.

### Which token creates a repo where

Creating a repo needs more than the push access the sync workflows use, and
the two PAT kinds behave differently:

- A **classic PAT with `repo` scope** can create repos under **the user who
  owns the token**, and under any org that user can create repos in. One
  classic PAT covers both `RokctAI` and a personal account.
- A **fine-grained PAT is bound to a single resource owner chosen when the
  token is issued**. A fine-grained token issued for the `RokctAI` org
  **cannot** create repos in a personal account, and vice versa — the target
  owner is not among its resources, so the call 404s. Covering both owners
  with fine-grained tokens takes two tokens.

So:

| Target owner | Token to use | Where to put it |
| :--- | :--- | :--- |
| `RokctAI` (default) | classic PAT with `repo` scope owned by a member who can create repos in the org, **or** a fine-grained PAT whose resource owner is `RokctAI` with Administration: write | `MONOREPO_PAT` — the existing credential, provided its scopes cover creation and not just push |
| a personal account (per-issue override) | classic PAT with `repo` scope owned by that user, **or** a fine-grained PAT whose resource owner is that user with Administration: write | `FACTORY_PAT`, since an org-scoped `MONOREPO_PAT` cannot reach it |

`app_create.yml` checks the token up front and fails with the required scope
named, rather than letting a bare 404 surface from the creation call.

## Why the org, not a personal account

Apps are born inside `RokctAI` rather than in a personal account and promoted
in later, because the protocol treats the two differently on purpose.
`initiate.py` withholds the `.rok` skill and the Protocol workflows
(`agent.yml`, `branch-cleanup.yml`, `play-deploy.yml`) from any repo whose
origin is not `RokctAI/*`, and it has no unattended path for choosing a
workspace outside the org — the non-org branch is an `input()` prompt with no
`CI` guard, which is an `EOFError` in any headless run. Spawning inside the
org means a new app gets the full protocol treatment on its first
`bootstrap.sh` and the factory special-cases nothing.

## Promoting an app out of the org

An app that outgrows the org — or that should sit under a personal account —
moves with GitHub's native **Settings → Transfer ownership**, which preserves
issues, PRs and stars and leaves redirects behind; nothing in this factory
needs to be involved. Note that after such a transfer the repo's origin is no
longer `RokctAI/*`, so a later `initiate.py` run there loses the `.rok` skill
and hits the unguarded prompt — commit a `.rokct/.workspace_config.json` in
the transferred repo before re-running it.

## The scaffold

`templates/app/` is what every new repo starts as. Files are copied verbatim
with `{{TOKEN}}` placeholders substituted by
`.github/scripts/seed_app_repo.py`:

| Token | Source |
| :--- | :--- |
| `{{APP_NAME}}` | issue form, *App name* |
| `{{APP_DESCRIPTION}}` | issue form, *One-line description* |
| `{{APP_SPEC}}` | issue form, *Rationale*, verbatim |
| `{{APP_OWNER}}` / `{{APP_REPO}}` / `{{APP_VISIBILITY}}` | resolved owner and visibility |
| `{{SOURCE_ISSUE}}` | URL of the accepted issue |

Contents: `README.md`, `AGENTS.md` (the agent's build brief), `.gitignore`
(stored as `gitignore` so it does not act on the factory's own tree),
`docs/spec.md` (the accepted brief, verbatim) and a `.rokct/` bootstrap —
`bootstrap.sh`, which fetches `initiate.py` from `RokctAI/The-Rokct-Protocol`
and runs it. The protocol is fetched rather than vendored so spawned repos
never ship a stale copy.

### Why the scaffold ships no `.workspace_config.json`

An earlier draft of this scaffold committed an empty `.workspace_config.json`
to keep a personally-owned repo out of `initiate.py`'s unguarded `input()`
prompt. With `RokctAI` as the target owner that file is redundant: the spawn
pushes to a `RokctAI/<app>` remote, so at bootstrap time the origin already
matches the org test at `profiles/local/initiate.py:484`, the script routes
`parent_repo` to `RokctAI/occultation` itself and never reaches the prompt at
`:488`. Shipping a config the protocol derives one line later only invites the
two to drift, so it was deleted. Verified by running the bootstrap in a scratch
repo with origin `https://github.com/RokctAI/newapp.git` and stdin closed: exit
0, `.rok` installed, `.rokct/.workspace_config.json` written pointing at
`RokctAI/occultation`.

Two caveats worth knowing:

- **Working files sync to `RokctAI/occultation`.** That is the org's shared
  workspace repo and it is what the protocol picks for every `RokctAI/*` repo;
  a spawned app is no exception. If an app should sync nowhere, commit a
  `.rokct/.workspace_config.json` with an empty `parent_repo` in *that* repo
  before bootstrapping — `initiate.py:520` and `sync_workspace.py:183` both
  treat empty as standalone.
- `initiate.py` skips deploying `sync_workspace.yml` and `maintenance.yml`
  when `CI` is set, so a bootstrap run inside a workflow installs `.rokct/`
  only. Run `bootstrap.sh` from an agent or developer session — which is what
  the **Build v0** issue asks for.

## Reusing the creation step

`app_create.yml` is a `workflow_call` workflow taking `name`, `description`,
`visibility`, `owner`, and optionally `spec` and `source_issue`; it takes
`FACTORY_PAT` as a secret (the caller resolves which token that is) and
returns `repo_url`. A second front-end — say a
merged PR that adds an app folder — can call it without going through issues.
